# PR 332: verification and Java memory investigation

These are read-only rules for compare-db-tool. They never call the write-capable
`refresh_client_cash_balances` routine. Only the existing optimized input function
is called; its temporary stages are allowed on non-production and rolled back by
the tool. No datasource settings, credentials or business data are changed.

## Delivered rules

| Rule | Question |
|---|---|
| `cash-refresh-20-environment-cfs.xml` | Actual valuation dates, installed function versions, and prerequisite row counts. Run first. |
| `cash-refresh-21-volume-and-mapping-cfs.xml` | Full BU input count, filtered Java report count, JSON payload bytes, workbook cell upper bound, Excel row limit, row-date agreement, and multiply/divide mapping differences. |
| `cash-refresh-22-output-preview-cfs.xml` | Compare persisted fixing, balance and contract outputs with a SELECT-only preview of the candidate formulas on the same input state. |

Rules 21-23 are generated by `python tools/generate-cash-refresh-rules.py` from
the versioned v2 SQL. Their internal SELECT-all CTEs deliberately retain intermediate
columns from that formula source; final returned column lists are explicit. This
accounts for the tool's SELECT-all advice. All standalone evidence queries use
full export, with expectations and ZIP packaging.

The same four XML files are copied into `D:\taomish\compare-db-tool\rules`.
The authoritative copies travel in this PR under `verification/cash-refresh`.

## How to run

Read the tool's AGENTS.md and complete HOW-TO-USE.md first. Use its existing JDK 21
launcher and credentials. Do not pass the production or apply flags.

```powershell
cd D:\taomish\compare-db-tool
$env:JAVA_HOME='D:\software\jdk-21.0.7'
.\compare.ps1 --rules rules\cash-refresh-20-environment-cfs.xml --target-env postgres-uat --validate
.\compare.ps1 --rules rules\cash-refresh-20-environment-cfs.xml --target-env postgres-uat --check
.\compare.ps1 --rules rules\cash-refresh-20-environment-cfs.xml --target-env postgres-uat --export none
```

Read `SUMMARY.md`, then the small full CSVs. Set the next rule's dates to the
**actual pinned fixture**; do not assume previous COB is a business-day subtraction.
The supplied October dates are historical examples. Date overrides do not alter
the database valuation date and do not reconstruct historical inputs. To test
01-Oct, an isolated copy must already contain its correct valuation and source state.

Example for that correctly aligned historical copy:

```powershell
$rule='rules\cash-refresh-21-volume-and-mapping-cfs.xml'
$scope=@('--target-env','postgres-uat',
         '--param','valueDate=2026-10-02','--param','cob=2026-10-01',
         '--param','prevCob=2026-09-30')
.\compare.ps1 --rules $rule @scope --validate
.\compare.ps1 --rules $rule @scope --check
.\compare.ps1 --rules $rule @scope --export none
```

Run each subsequent rule individually with validation and live checking first.
Use `--param clientFilter=OCF --param currencyFilter=USD` in rule 21 to measure a
screen-filtered workbook. Calculations and parity previews remain BU-wide.
The first invocation of the optimized input function may be expensive. Do not
start many copies in parallel. Non-production datasource policy must allow this
temporary-table function; the current datasource listing permits it on UAT.

Exit 0 means the stated checks passed; exit 1 means differences/check failures;
exit 2 means an error or incomplete result. Read `SUMMARY.md`, `FINDINGS.md`,
`EXPECTATIONS.md`, `CHECK.md` and `TIMINGS.csv`; send the generated ZIP.

## What rule 22 proves and what it does not

Take an isolated, quiescent copy with matching tenant, BU, valuation dates,
previous balances, pricing, fixings and manual fields. Run the old Java refresh
on it first if the baseline should represent that endpoint. Rule 22 then reads
its persisted outputs and compares all three output types against the candidate
SELECT preview. Numeric tolerance is 0.000001; audit UUIDs and timestamps are not
business-value comparison keys. Row/key differences are not silently accepted.

The rule does not start Java, install the new function, execute its writes, run
Liquibase, render Excel or prove endpoint timing. Existing persisted outputs may
be stale or manually edited. A disagreement is evidence to investigate, not
automatic proof that the candidate is wrong. Complete before/after execution on
an isolated copy remains required before merging.

The generated SELECT preview is checked locally against all three tables written
by the real candidate function using the regression harness. This is separate
from real-data parity and from Java integration.

## Java heap: the remaining cost

Refresh calculations now stay in PostgreSQL. Java receives the missing-client
list and the **filtered raw report rows for Excel**, not just aggregated balances.
Those rows are still materialized by `queryForList` into maps. The client sheets
can duplicate rows from RawData in the workbook. A compressed XLSX response and
ByteArrayOutputStream buffer also coexist briefly on heap.

The refresh workbook now uses SXSSFWorkbook with a 100-row window, compressed
temporary files, and an explicit flush after each completed sheet. This removes
the all-cells-in-memory XSSFWorkbook cost; it does not bound the raw map list or
final response bytes. It trades workbook cell memory for temporary disk usage.

Rule 21 returns only aggregates to the comparison tool:

- `bu_report_rows`: rows calculated in PostgreSQL for the whole BU.
- `java_report_rows`: rows Java would load for the selected workbook filters.
- `json_payload_bytes`: serialized row size, **not Java retained heap**.
- `workbook_cells_upper`: upper bound including RawData and client-sheet copies.
- `exceeds_excel_sheet_limit`: RawData cannot fit if over 1,048,575 data rows.

Do not convert JSON bytes to a guaranteed heap size using an arbitrary multiplier.
For heap safety, run one representative endpoint request with the deployed heap
limit and concurrency and record peak/retained heap, response size, GC activity,
temporary-disk use and full endpoint duration (JFR or equivalent). The checked-in
Dockerfile sets no explicit Xmx; deployed limits were not inspected. For very
large map lists the next design step is streaming the report rows from JDBC or
a paged export job, together with streaming the HTTP/archive bytes.

## Behaviour decisions deliberately retained

- Spot mapping is the legacy/PR-331 source; differences from the BU threshold view
  are exposed by rule 21, not silently reverted.
- Inclusive 1e-10 tolerance and manual-entry preservation remain intentional.
- No parameter here enables writes or resets manual values.

## Verification performed in this revision

- Local SQL regression, including SELECT-preview vs real-function outputs, and
  the two-session fail-fast lock probe were executed separately.
- Four rules validated offline with compare-db-tool.
- The two-changeset refresh XML validated offline through Liquibase.
- UAT and dev environment checks both failed to connect after approximately 10 s.
  No real row count, mapping parity, October result or production timing was read.
- Java build/startup and workbook visual/heap profiling remain unverified.
